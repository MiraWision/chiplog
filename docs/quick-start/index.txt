10:T45f6,<h1 id="quick-start"><a class="anchor" href="#quick-start" aria-label="Link to this section">Quick start</a></h1><p>chiplog turns one operation into one log record. You mark the steps; it accumulates them, times
them, and flushes a single wide event when the operation settles.</p>

Reading down the list tells you where the 173 ms went without any extra instrumentation.</p>
<div class="callout callout-pass"><p class="callout-label">Tip</p><p>Name flows after the operation, not the transport: <code>checkout.submit</code>, <code>jobs.reindex</code>,
<code>bullhorn.sync</code>. The framework adapters use <code>http.&lt;METHOD&gt; &lt;route&gt;</code> because for an HTTP entry point
the route <em>is</em> the operation.</p>
</div><h2 id="where-to-put-flows"><a class="anchor" href="#where-to-put-flows" aria-label="Link to this section">Where to put flows</a></h2><p>Not everywhere. A flow is worth it where an operation has several steps that can each fail, and where
&quot;what happened to that one request&quot; is a question you actually ask.</p>
<p>Good candidates: HTTP entry points, queue consumers, scheduled jobs, anything that calls a third
party, anything an LLM touches.</p>
<p>Poor candidates: pure functions, hot loops, getters. <code>stage()</code> is cheap, but an event per array
element is noise.</p>
